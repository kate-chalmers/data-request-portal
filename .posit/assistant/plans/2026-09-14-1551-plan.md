# Plan: Make Google Drive session storage non-blocking

## Problem

Since sessions moved to Google Drive (`pins::board_gdrive`), the app feels slow or frozen:

- The auto-save observer in `app.R` (~line 1853) fires on **every change** to any
  `session_data` field and does a **synchronous** `pin_write()` of the entire session.
  Each Drive write is several sequential API calls (~2–6+ s).
- Button handlers (submit, save-and-continue, revert-to-default, final submit) all
  mutate `session_data`, so each click blocks on a full Drive round trip before the
  UI updates — the app "looks like it's not working".
- The freeze-poll observer (~line 1897) does a full `session_read()` of the country
  session every 30 s — another blocking multi-second call. Since shinyapps.io serves
  multiple users per R process, one user's Drive call blocks *everyone* on that worker.

Constraint confirmed with user: storage must stay in the current Google account, so we
keep Drive and optimize around it.

## Approach

Three changes, in order of impact:

### 1. Debounce + coalesce the auto-save (biggest win)

- Replace the eager auto-save observer with a **debounced payload reactive** (~5 s):
  edits update `session_data` instantly (UI stays snappy), and Drive only sees one
  write once the user pauses.
- Add a **dirty-flag coalescing pattern**: if a write is already in flight when new
  changes arrive, mark dirty and re-write with the latest payload when the in-flight
  write finishes. Never queue more than one pending write.
- Flush any dirty state in `session$onSessionEnded()` (synchronous, safe — session is
  over anyway) so the last few seconds of edits aren't lost when a user closes the tab.

### 2. Make Drive writes asynchronous (`mirai` + `ExtendedTask`)

- Add `mirai` daemons (1–2) at app startup in `global.R`; initialize the pins board
  inside each daemon via `mirai::everywhere()` (set `gargle_oauth_cache = "drive-token"`,
  `drive_auth()`, `board_gdrive(...)`), mirroring the existing token setup.
- Wrap `session_write()` in an `ExtendedTask` so writes happen off the main R process.
  Buttons return instantly; a failed write still shows the existing error notification.
- Explicit actions (submit, final submit) also go through the async path, but flush
  immediately (skip the debounce) and show a transient "Saving…" → "Saved" status so
  users get confirmation without blocking.
- Keep the existing synchronous `session_write()` as a fallback if daemons fail to
  start (e.g., local dev without mirai installed).

### 3. Cheapen the freeze poll

- Move admin freeze flags out of the (large) per-country session pins into one tiny
  shared `"frozen"` pin (named list `iso -> frozen_at`), written only by the admin
  freeze/unfreeze buttons.
- The 30 s poll then reads one small pin (and can be made async too / lengthened to
  60 s), instead of re-downloading the full country session every 30 s per user.
- Migration: on first read, if the `"frozen"` pin doesn't exist, fall back to the old
  per-session `frozen` field so no state is lost.

### 4. UI feedback (small, cheap)

- Add a small save-status indicator ("Saving…" / "All changes saved ✓" with timestamp)
  so slow-but-working moments are visible instead of looking broken. Reuses the
  existing `tu_meta_saved_at` pattern.

## Files touched

| File | Change |
|---|---|
| `global.R` | mirai daemon setup + async `session_write_async()`; `"frozen"` pin helpers |
| `app.R` | Debounced/coalesced auto-save; async submit/final-submit; new freeze poll; save-status indicator; `onSessionEnded` flush |
| (deps) | Add `mirai` to the deployment bundle |

## Out of scope (possible follow-ups)

- Admin panel reads of *all* country sessions (slow but admin-only).
- Migrating to a database backend (ruled out for now — must stay in the Google account).
- Login-time `session_read()` stays synchronous (one-time cost; could get a spinner).

## Risks / notes

- mirai daemons run inside the shinyapps.io container — supported, but we keep the
  synchronous fallback in case daemons can't start.
- Async writes mean a worker crash could lose up to ~5 s of edits (previously 0 s but
  with a frozen UI). The `onSessionEnded` flush covers normal tab closes.
- Last-write-wins semantics are unchanged from today.

## Verification

1. Run locally with the local-folder fallback board: confirm edits, submit, and
   revert-to-default respond instantly and the debounced write fires after ~5 s.
2. Run locally with the Drive token: confirm writes land on Drive, coalescing works
   (rapid edits → few writes), and the save indicator cycles correctly.
3. Test freeze/unfreeze from the admin view with a second logged-in session.
4. Deploy to shinyapps.io and smoke-test submit + revert + close-tab flush.
